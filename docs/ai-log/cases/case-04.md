# case-04 — SOLID 규칙 점검: AI의 과한 규칙을 비용·복잡도로 반박하고, 재료 분기를 switch로 결정

단계/태스크: 2단계 설계 준비 / CLAUDE.md v1 · 일시: 11-19 · 판정: (사용자 기입: 채택 / 수정 / 기각)

## 1. 문제 — 상황과 제약
- CLAUDE.md v1을 확정하기 전에, SOLID를 지키는 코딩 컨벤션과 "뻔한 구현 대신 SOLID를 적용한 곳"을 표시하는 주석 규칙을 넣고 싶었다
- 제약: 5일, C++ 클래스 8개 이하, 함수·변수를 무작정 늘리지 않는다

## 2. 요청 변화 — 요청 → 반박 → 결정 → 정정
- 요청: SOLID 원칙을 지키는 코딩 컨벤션 + 적용 지점 표시 주석
- 반박 (AI 1차 제안에 대해)
  - S: "그리고"로 묶인 기능이 간단한 코드라면 분리 자체가 오버헤드 아닌가
  - O: DataTable 조회를 자주 하면 오버헤드 아닌가, 시간복잡도는?
  - L: Super 호출을 고정하는 게 맞나, 완전히 재정의해야 하는 경우도 있지 않나
- 결정: 재료는 고정이므로 재료 분기는 switch로 구현한다
- 정정 (AI 해석 오류에 대해): 재료 분기만 switch, 데이터는 DataTable로 관리한다

## 3. AI 결과 요약 (원본: Claude 채팅 기록 — 링크 기입)
- AI 1차 제안
  - S: 책임 한 줄에 '그리고'가 필요하면 분리를 검토
  - O: 늘어날 수 있는 항목(재료·조합·일차·찜기 레벨)은 switch/if 나열 대신 DataTable 조회
  - L: 엔진 가상 함수를 override하면 Super 호출
  - I·D: BP 노출 최소화, 로직이 위젯을 참조하지 않음 / 구현체가 하나뿐인 UInterface 금지
  - 표시 주석: `// SOLID-<S|O|L|I|D>: <버린 방식> 대신 <택한 방식> — <얻는 것>`
- AI 2차 (반박 후 수정)
  - S: 기준을 기능 개수가 아니라 '바뀌는 이유'로. 같은 이유로 바뀌거나 코드가 작으면 합쳐 둔다
  - O: FindRow는 RowMap(TMap) 해시 조회라 평균 O(1). 이 게임의 조회는 이벤트 빈도라 switch와 차이가 없다. 고정 집합은 enum + switch가 맞다
  - L: 생명주기 함수(BeginPlay·EndPlay 등)만 Super 필수. 동작을 대체할 때는 생략할 수 있되 이유를 주석에 적고, 부모의 결과 계약은 지킨다
- 이후 흐름
  1. 사용자: 재료는 고정이니 재료 분기를 switch로 결정
  2. AI: 결정을 "수치 전체(재료·일차·찜기·밸런스)를 코드로"로 넓혀 해석하고 CLAUDE.md 최종본 작성
  3. 사용자: "재료만 switch, 데이터는 DataTable"로 정정
  4. AI: O 재작성 — 수치는 DataTable(FindRow), 고정 집합(재료·작업대 상태·입력 종류)은 enum + switch(default 없이 checkNoEntry()), 캐시는 반복 경로가 생길 때만
  5. 같은 흐름에서 사용자가 단순성 원칙을 추가 → ADR-0003
