# AIGame — 데이터 스키마

> 2단계 산출물 · 2026-11-19 · 원본: `Data/*.csv` → DataTable (ADR-0013)
> CSV 컬럼을 바꾸면 Row 구조체와 이 문서를 같은 변경에서 고친다(CLAUDE.md 53행). Row 구조체 멤버 순서 = CSV 컬럼 순서(92행).
> 수치 값은 5단계에서 채운다. 이 문서는 컬럼 · 타입 · 키 · 제약만 정한다.

## 공통 규칙
- 키: CSV 첫 열(헤더 `---`)이 DataTable 행 이름(FName)이다. Row 구조체에는 키를 다시 넣지 않는다.
- 단위: 시간은 초(float), 금액은 골드(int32), 확률은 0~1(float).
- CSV에는 수치와 화면 이름(FText)만 둔다. 이미지 에셋은 BP 기본값에 둔다(ADR-0014).
- DataTable 에셋(`DT_*`)은 사람이 CSV를 가져와 만든다(Content/ 수정은 사람 작업). GameInstance BP가 직접 참조해 APK 쿡에 포함되게 한다 → 첫 APK에서 확인.
- 자동화 테스트는 DataTable을 읽지 않고 Row 구조체를 코드에서 만들어 넣는다(architecture.md 1.6).

## Ingredients.csv → `DT_Ingredients` · `FIngredientRow`
| 열 | 타입 | 뜻 | 제약 |
|---|---|---|---|
| (행 이름) | FName | `EIngredient` 값 이름: RedBean(팥) · Yogurt · DubaiChoco · Strawberry · Blueberry · Pineapple · Mango | enum 값과 1:1. `None`은 행 없음 |
| DisplayName | FText | 화면 이름(로비의 다음 해금 표시) | 비어 있지 않음 |
| UnlockOrder | int32 | 해금 순서. 0 = 처음부터 해금 | 0이 하나(팥), 1~6이 빠짐 · 중복 없이 |
| UnlockCost | int32 | 해금 비용 | UnlockOrder 0이면 0 |
| Cost | int32 | 작업대에 올리는 순간 차감되는 재료비 | ≥ 0 |
| Price | int32 | 판매가 계산에 쓰는 값 | > 0 |
| OrderWeight | int32 | 주문 가중치. 베이스는 베이스끼리, 과일은 과일끼리(+ Balance.NoFruitWeight) 비교 | ≥ 0 |
| RentIncrease | int32 | 이 재료를 해금하면 하루 임대료가 이만큼 오른다(ADR-0017) | ≥ 0 |

- 행 이름 ↔ enum: `UEnum::GetNameStringByValue`(`Runtime/CoreUObject/Public/UObject/Class.h` 2221행)로 행 이름을 만든다. 반환 형식(접두사 유무)은 구현 때 테스트로 확인한다. 행 이름 영문 표기는 [AI 판단].
- Base / Fruit 구분은 CSV에 두지 않는다 — 코드의 `EIngredient` switch가 원본이다(2.2).
- 해금 상태: `FShopProgress.UnlockStep`(정수). UnlockOrder ≤ UnlockStep인 재료가 해금된 것이다.
- 조합 15종은 해금된 재료로 계산하고 저장하지 않는다.
- 조합 판매가: 과일 없음 → 베이스 Price. 과일 있음 → `FMath::RoundToInt((베이스 Price + 과일 Price) × MixMultiplier)` (`Runtime/Core/Public/GenericPlatform/GenericPlatformMath.h` 323행).
- GDD 원안에서 바뀐 열: IngredientId → 행 이름, Name → DisplayName, Type · Icon 삭제(코드 · BP로 이동), RentIncrease 추가.

| 열 | 타입 | 뜻 | 제약 |

- GDD 원안에서 바뀐 것: Key/Value 형식 → 한 행 형식, MaxStockPerRecipe · BaseRent 추가.

## CSV 밖에 두는 것 (ADR-0014)
| 대상 | 위치 | 비고 |
|---|---|---|
| 재료 아이콘(재료통 · 말풍선) · 제품 겹침 이미지 | BP 기본값 (`EIngredient` → 텍스처) | 아이콘과 겹침 이미지를 같은 그림으로 쓸지는 아트 작업 때 정한다 |
| 사람 외형 3~4종 | C++ UPROPERTY 배열을 BP에서 채움 | 로직은 배열 길이를 외형 수로 쓴다. 데이터에 외형 수를 따로 두지 않는다 |
| "아무거나" 아이콘 · 쓰레기 모자이크 | 위젯 | — |
- 정확한 소유 클래스와 프로퍼티는 3단계에서 정한다.

## 데이터 검증
- 앱 시작 때 한 번, 데이터가 들어오는 경계에서 검사한다(CLAUDE.md 66행): enum 값마다 Ingredients 행이 있는지, Days · Steamer 행 이름이 "1"부터 행 수까지 빠짐없는지(T03 사용자 결정 — `FillDayInput`의 min(Day, 행 수) 조회와 '최대 레벨 = 행 수'의 전제), Balance의 `Default` 행이 있는지, MaxQueue 1~5, ArrivalMin > 0 · ArrivalMin ≤ ArrivalMax(블라인드 리뷰 반영 — 간격이 0 이하면 도착 이벤트 처리가 끝나지 않는다), Steamer 행마다 MaxGauge > 0 · RegenTime > 0(T12 사용자 결정 — MaxGauge가 0이면 하루 종일 찜기를 쓸 수 없다), UnlockOrder 0~6 빠짐 · 중복 없음, RentIncrease ≥ 0, BaseRent < StartGold, MaxStockPerRecipe ≥ 1(T13 사용자 결정 — 배분이 진열대 새 칸을 개수 1로 넣는 전제), 구매 비용 > 0(UnlockOrder ≥ 1의 UnlockCost, 레벨 2 이상의 UpgradeCost — `FShopProgress::TrySpend`의 전제, T02 사용자 결정).
- 실패 처리: `checkf`로 멈춘다(architecture.md 3.5 `Init`). 메시지는 영어로 테이블 · 행 · 값을 적는다.



## 수치 초안 (5단계) — 아래 값은 모두 [초안]
> 원본은 `Data/*.csv`다. CSV에는 표시를 붙일 수 없어 [초안] 표시와 산정 근거는 이 절에 둔다. 플레이 테스트 후 확정하면 이 절의 [초안]을 지운다.
> 한글 DisplayName: UE는 BOM 없는 CSV도 UTF-8로 읽는다(`Runtime/Core/Private/Misc/FileHelper.cpp` 123~134행). 첫 가져오기 때 글자가 깨지지 않는지 확인한다.

### 산정 목표
1. 1일차는 누구나 손님을 모두 받는다(놓침 0) — 조작을 익히는 날
2. 일차가 오를수록 빨라진다(GDD). 느리거나 서툰 플레이어는 중반부터 손님을 놓친다
3. 6단계 해금 완료: 보통 플레이어 약 5일차 (하루 3분 → 약 15분 플레이). 사용자 결정(2026-11-24): 손님 방문 속도를 1.5배로 올리면서 첫 목표(6~7일차, 약 20분)보다 당겨진 결과를 받아들였다
4. 해금할수록 조합 이익이 커진다(성장 루프). 뒤 재료는 재료비와 함께 판매가도 높다(D18)
5. 파산은 요거트 · 파인애플 · 두바이초코를 해금해 임대료가 오른 직후, 실수가 많은 플레이어에게 일어난다(D18). 보통 · 느림 플레이어는 파산하지 않는다
6. 뒤에 해금되는 재료일수록 해금 비용 · 재료비 · 판매가가 높다(GDD) — 해금 순서대로 모두 증가
7. 모든 조합의 판매가 > 재료비(떡 포함)

### 설계 의도: 임대료로 해금의 대가를 만든다
- 서툰 · 실수 많은 플레이어는 손이 느려 하루 이익(매출 − 재료비)이 해금 단계와 거의 상관없이 2일차부터 320~400에 머문다. 보통 플레이어는 일차가 오를수록 540~1130까지 는다(시뮬레이션 측정).
- 그래서 임대료를 해금 단계마다 서툰 플레이어의 하루 이익 근처까지 올린다. 그 재료를 해금한 직후 서툰 플레이어만 적자가 날 수 있다.
- 임대료를 올리는 재료: 팥을 뺀 베이스 2종(요거트 · 두바이초코) + 가운데 순서의 과일 1종(파인애플, 전체 해금 순서 4번째). 블루베리안과 비교해, 파산이 요거트와 파인애플 두 단계에 나뉘어 일어나는 파인애플안을 골랐다. 다른 재료로 바꾸려면 CSV의 RentIncrease만 옮긴다.
- 두바이초코의 증가분은 거기까지 간 플레이어(보통 · 느림)의 성장 속도만 늦춘다. 서툰 플레이어는 대부분 그 전에 멈추거나 파산한다.

### Days.csv
| 일차 | Duration | ArrivalMin | ArrivalMax | Patience | MaxQueue | AnyOrderRate |
|---|---|---|---|---|---|---|
| 1 | 180 | 3.7 | 5.7 | 25 | 3 | 0.10 |

- 영업 시간은 GDD "하루 약 3분". 도착 간격은 일차마다 약 15% 줄고, 인내심은 25초에서 15초로 줄며, 대기열은 3에서 5(화면 슬롯 수)까지 는다. 7일차부터는 6일차 값을 쓴다.
- 도착 간격은 첫 초안(1일차 5.5~8.5초 … 6일차 2.0~4.0초)을 1.5로 나눠 소수 첫째 자리로 반올림한 값이다 — 사용자 결정(2026-11-24 실기기 플레이: 손님이 느려 긴장감이 없음, 요청 범위 1.5~2배).
- 1.5배를 고른 이유: 하루 판매 수는 손 속도와 찜기가 상한이다(보통 약 57 · 느림 약 38 · 서툰 약 29개). 그보다 빨리 오는 손님은 매출이 되지 않고 놓침이나 '대기열이 꽉 차 돌아감'이 된다. 2배는 6일차 판매가 1.5배와 같고(보통 57개), 1일차부터 서툰 플레이어 손님의 약 1/3(도착 51명 중 17명)이 돌아간다. 1.5배에서는 약 4명(도착 38명 중)이다. 비교는 대기열이 꽉 차 돌아간 손님까지 센 별도 실행(balance_sim.py를 그대로 쓰고 간격만 나눔, 시드 30개)으로 했다.

- 방법: architecture.md 3.6의 영업 규칙을 단순화해 따라가는 Python 시뮬레이션(AI 작성). 시드 30개 평균, 10일. 로비에서는 살 수 있는 것을 바로 산다(해금 직후의 위험을 그대로 겪는다).
- 플레이어 모델 5종: 탭 간격 · 제품마다 판단 시간 · 재료 탭마다 실수 확률. 한계는 스크립트 머리말에 적었다(미리 쌓아 두기 없음, 배분 시각 근사, 실력이 늘지 않음).

| 플레이어 | 탭 간격 · 판단 · 탭당 실수 | 6단계 해금 완료 | 빚 경고 경험 | 파산 (해금 단계: 횟수) |
|---|---|---|---|---|
| 보통 | 0.5초 · 0.5초 · 2.5% | 5.0일차 | 0/30 | 0/30 |
| 느림 | 0.8초 · 1.0초 · 5% | 7.3일차 | 1/30 | 0/30 |
| 서툰 | 1.0초 · 1.5초 · 10% | 없음 | 6/30 | 2/30 (파인애플 뒤 2) |
| 실수 많음 | 0.8초 · 1.0초 · 16.5% | 없음 | 19/30 | 9/30 (파인애플 뒤 9) |
| 실수 아주 많음 | 0.8초 · 1.0초 · 22.5% | 없음 | 28/30 | 23/30 (요거트 뒤 20 · 파인애플 뒤 3) |

| 일차 | 보통: 임대료 / 순이익 / 해금 단계 | 서툰: 임대료 / 순이익 / 해금 단계 |

- 목표 1 · 3 · 4 · 5 · 6 · 7을 만족한다. 목표 1은 놓침(인내심 만료) 기준이다 — 대기열이 꽉 차 돌아간 손님은 balance_sim.py가 세지 않으며, 위 별도 실행에서 1일차 서툰 플레이어는 도착 약 38명 중 약 4명이 돌아갔다.
- 목표 2는 만족하지만 놓치기 시작하는 일차가 당겨졌다: 서툰 2일차 · 느림 3일차 · 보통 5일차부터 놓친다(보통은 6일차부터 하루 약 14명).
- 서툰 플레이어는 요거트 해금(2일차 끝) 직후 순이익이 317 → 89로 떨어지고, 파인애플까지 해금하면 13~45로 줄어 이후 파산하거나 제자리에 머문다.
