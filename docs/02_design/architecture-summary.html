1게임 루프

로비 — 재료 해금 · 찜기 업그레이드→ 영업 약 3분 — 손님 주문대로 모찌 조립 · 판매→ 결산 — 순이익 반영 · 저장→ 다음 날

재료를 하나씩 해금할수록 더 비싼 조합을 팔 수 있지만, 일부 재료는 해금하는 순간 가게 임대료가 오릅니다. 목표는 재료 6단계 해금, 실패는 빚으로 마감한 다음 날도 빚으로 마감하는 파산 한 가지입니다.

3클래스와 책임

행동(규칙)을 가진 C++ 클래스는 넷뿐이고, 나머지는 이들이 들고 있는 데이터입니다.

이름사는 곳한 줄 책임검증
UShopGameInstance앱 전체앱 전체 진행 상태의 주인. 저장 · 불러오기, 로비 구매, 하루 결과 반영을 맡는다PIE · 실기기
FShopProgressGameInstance 안 · 저장 파일진행 값(일차 · 골드 · 해금 단계 · 찜기 레벨)과 구매 · 결산 · 파산 규칙자동화 테스트
UShopSaveGame저장 · 불러오기 순간저장 슬롯에 쓰는 진행 값 묶음(저장 버전 포함)PIE · 실기기
ABusinessGameMode영업 레벨영업의 진행자. 월드 시간과 타이머 1개로 규칙을 돌리고, 화면의 입력과 알림을 이어 준다PIE · 실기기
FBusinessSim영업 레벨(GameMode 안)하루 영업의 규칙 전체 — 손님 · 주문 · 인내심, 작업대 · 찜기, 배분 · 진열대, 집계. 현재 시각을 인자로 받아 계산한다자동화 테스트
로비 · 영업 화면각 레벨블루프린트 위젯. 로직이 알려 주면 데이터를 읽어 다시 그린다. 로직은 화면을 모른다사람 확인
왜 이렇게 나눴나? 레벨을 로비와 영업으로 나눠, 하루 영업 상태는 레벨이 바뀌면 통째로 정리됩니다. 영업 규칙(FBusinessSim)은 엔진에 기대지 않는 일반 클래스라 월드 없이 시간을 넣어 가며 테스트할 수 있습니다.

4클래스가 아니라 데이터인 것

손님이나 작업대는 화면에 보이지만 따로 클래스로 만들지 않았습니다. 손님의 행동(도착 · 이탈 · 구매)은 대기열 전체를 봐야 하는 규칙이라, 대기열을 가진 FBusinessSim이 처리합니다. 그림은 위젯이 이 데이터를 읽어 그립니다.

손님

대기열의 한 줄(주문 · 외형 · 인내심 만료 시각). 화면에서는 가로로 줄 선 사람 이미지 최대 5명, 머리 위 말풍선에 주문.

모찌 조합

베이스 1개 + 과일 0~1개라는 값. 주문과 완성품이 같은 모양이다. 화면에서는 베이스 이미지 위에 과일 이미지를 겹쳐 그린다.

재료

고정된 7종류의 열거형. 가격 같은 수치는 기획 데이터 표에서 읽는다.

작업대

상태 하나(비어 있음 · 베이스 · 베이스+과일 · 감싸는 중 · 쓰레기)와 올려 둔 재료.

찜기

떡 게이지 숫자. 0이 되면 정해진 시간 동안 다시 찐다.

진열대

처음 진열된 순서의 (조합, 개수) 목록. 화면은 3행 × 5열 칸에 제품 이미지와 개수를 표시한다.

5영업 하루의 흐름

  1. 영업 시작 — 로비에서 영업 레벨을 열면 ABusinessGameMode가 진행 값과 기획 수치를 받아 하루를 시작한다. 이때 임대료를 낸다.
  2. 손님 도착 — 일차별 간격으로 손님이 온다. 원하는 모찌가 진열대에 있으면 바로 사 가고, 없으면 줄을 선다(최대 5명).
  3. 제작 — 플레이어가 재료통 · 찜기를 탭한다. 재료비는 탭하는 순간 빠지고, 작업대 상태가 바뀐다.
  4. 배분 — 모찌가 완성되면 그 조합이나 “아무거나”를 주문한 손님 중 가장 먼저 온 손님에게 팔린다. 기다리는 손님이 없으면 진열대로, 그 조합이 이미 가득(5개)이면 폐기.
  5. 이탈 — 인내심이 다한 손님은 매출 없이 떠난다.
  6. 영업 종료 — 약 3분 뒤 남은 재고와 작업대 위 재료는 폐기되고 기다리던 손님은 돌아간다.
  7. 결산 · 저장 — 순이익(매출 − 재료비 − 임대료)을 진행 값에 반영하고 즉시 저장한다. 이틀 연속 빚이면 파산 → 저장을 초기화하고 1일차부터.

6시간은 어떻게 흐르나

  • 시간 기준은 하나 — 엔진의 월드 시간. 게임을 일시정지하면 함께 멈춘다.
  • 규칙은 시계를 직접 읽지 않는다 — FBusinessSim의 모든 계산은 “현재 시각”을 인자로 받는다. 게임에서는 GameMode가 월드 시간을 넣고, 테스트에서는 원하는 시각을 직접 넣어 30초를 기다리지 않고 건너뛴다.
  • 매 프레임 검사(Tick)를 쓰지 않는다 — 손님 도착 · 인내심 만료 · 찜기 재생성 완료 · 작업대 연출 끝 · 영업 종료, 이 다섯 가지를 “일어날 시각” 순으로 정렬된 목록(최소 힙) 하나에 넣는다. 타이머 하나가 맨 앞 이벤트 시각에만 깨어나 처리한다.
  • 화면의 게이지 — 인내심 · 남은 시간은 “원래 시각 − 현재 시각”으로 위젯이 계산해 그린다. 일시정지 중에는 저절로 멈춘다.
앱이 백그라운드로 가면 영업 중이면 게임을 일시정지하고, 돌아오면 “계속하기” 오버레이를 띄운다. 일시정지 덕분에 백그라운드에 있던 시간이 영업 시간에 더해지지 않는다.

7제작 규칙

정해진 순서대로 탭하면 완성, 순서가 틀리면 그때까지 쓴 재료비를 잃고 쓰레기가 됩니다.

비어 있음베이스 → 베이스과일(선택) → 베이스 + 과일찜기 → 감싸는 중→ 완성 → 손님 · 진열대
쓰레기← 비어 있는데 과일 · 찜기, 베이스 위에 베이스, 과일 위에 과일 · 베이스, 또는 “버리기” 버튼
  • 재료를 올리거나 감싸거나 버리는 연출 중에는 재료통 · 찜기 · 버리기 입력을 무시한다(연타 방지). 일시정지는 언제나 된다.
  • 이 상태 전이표는 자동화 테스트가 표 그대로 검증한다.

8경제와 파산

판매가

베이스 단독이면 베이스 가격, 과일을 더하면 두 가격의 합에 혼합 배수를 곱한다. 뒤에 해금되는 재료일수록 비싸고 이익도 크다.

재료비

재료를 올리는 순간 빠진다. 골드가 모자라도 재료는 고를 수 있어, 영업 중에 잠깐 빚이 될 수 있다.

임대료

영업 시작 때 낸다. 기본 임대료에 더해 요거트 · 파인애플 · 두바이초코를 해금할 때마다 오른다.

파산

판정은 결산 때만 한다. 빚으로 마감한 다음 날도 빚이면 게임 오버. 로비 구매는 골드가 충분할 때만 된다.

설계 의도 임대료가 오르는 재료를 해금한 직후, 실수가 많은 플레이어는 하루 순이익이 0 아래로 떨어질 수 있습니다. 해금은 “더 많이 버는 길”이면서 “실수의 대가가 커지는 순간”입니다.

9저장과 앱 생명주기

  • 저장하는 것 — 저장 버전, 일차, 골드, 해금 단계, 찜기 레벨. 진행 값은 영업 중에 바뀌지 않고 결산 때 한 번 바뀐다.
  • 저장 시점 — 결산 확정 직후, 로비 구매 직후, 앱이 백그라운드로 갈 때.
  • 영업 중 강제 종료 — 진행 값이 영업 시작 때 그대로라, 다시 켜면 그날 영업을 처음부터 한다.
  • 게임 오버 — 확정되는 즉시 저장을 초기화한다(팝업에서 앱을 꺼서 피할 수 없다).

10기획 데이터는 어디에

수치는 코드에 쓰지 않고 표(CSV → DataTable) 네 개로 관리합니다. 재료를 하나 늘리려면 재료 종류 하나와 재료 표 한 줄을 추가하면 조합은 자동으로 늘어납니다.

표담는 것
재료해금 순서 · 해금 비용 · 재료비 · 판매가 · 주문 가중치 · 해금 때 오르는 임대료
일차영업 시간 · 손님 도착 간격 · 인내심 · 최대 대기 인원 · “아무거나” 확률 (마지막 일차 이후는 반복)
찜기레벨별 떡 게이지 · 다시 찌는 시간 · 업그레이드 비용
전역 상수시작 골드 · 떡 재료비 · 혼합 배수 · 연출(입력 잠금) 시간 · 진열 상한 · 기본 임대료
이미지(재료 아이콘 · 제품 이미지 · 손님 외형)는 표가 아니라 블루프린트 기본값에 둡니다. 화면 연출 자원이라 화면 쪽에 둔 것입니다.

11검증 방법과 시뮬레이션

설계 검증

  • 자동화 테스트 33개(예정) — 영업 규칙(FBusinessSim)과 진행 규칙(FShopProgress)을 월드 없이 검증한다. 손님 · 제작 · 찜기 · 배분 · 진열대 · 영업 종료 · 임대료 · 파산.
  • 시나리오 워크스루 6개 — 정상 하루와 예외 다섯 가지(연출 중 영업 종료, 일시정지 · 백그라운드, 쓰레기 · 버리기, 재고 손님 · “아무거나” 대기, 이틀 연속 빚 → 파산)를 설계대로 따라가며 빈틈 2건을 찾아 고쳤다.
  • 추적표 — 기획서의 모든 규칙이 담당 클래스와 검증 방법에 빠짐없이 연결되어 있다.

밸런스 시뮬레이션

영업 규칙을 단순화한 시뮬레이션으로 플레이어 유형 다섯 가지(보통 · 느림 · 서툰 · 실수 많음 · 실수 아주 많음)를 무작위 시드 30개씩, 10일 동안 돌려 일차별 순이익 · 해금 진행 · 파산 여부를 확인했습니다.

1일차는 모두 손님을 놓치지 않는다조작을 익히는 날
보통 · 느린 플레이어는 파산하지 않는다보통은 6~7일차, 느린 플레이어는 9일차쯤 해금 완료
실수가 많을수록 파산 위험이 커진다서툰 플레이어는 약 4명 중 1명, 실수가 많으면 3명 중 1명, 아주 많으면 3명 중 2명 꼴
파산은 해금 직후에 몰린다임대료가 오르는 요거트 · 파인애플 해금 직후
시뮬레이션의 플레이어는 실력이 늘지 않고 해금을 바로 삽니다. 실제 손맛과 “해금을 미루는 선택”은 기기에서 플레이 테스트로 다시 확인합니다.

12핵심 설계 결정

  • 로비와 영업을 별도 레벨로 — 하루 영업 상태가 레벨과 함께 통째로 정리된다.
  • 규칙은 엔진과 분리된 일반 클래스 — 현재 시각을 인자로 받아, 월드 없이 자동화 테스트한다.
  • 시간 이벤트는 힙 하나 + 타이머 하나 — 같은 시각 이벤트의 처리 순서까지 테스트로 재현된다.
  • 손님 · 작업대 등은 데이터, 그림은 위젯 — 로직은 화면을 모르고 알림만 보낸다. 손님은 포인터가 아니라 번호로 가리켜, 재사용된 화면 슬롯이 엉뚱한 손님을 가리키는 문제를 막는다.
  • 완성품은 도착 순 대기열을 한 번 훑어 배분 — 대기 손님이 5명 이하라 조합별 대기열을 따로 두지 않는다.
  • 진열대는 조합당 칸 하나 · 3 × 5 — 이미지 한 장과 개수 숫자, 조합당 최대 5개.
  • 수치는 표, 이미지는 블루프린트 — 밸런스를 바꿔도 테스트가 깨지지 않는다.
  • 해금 때 임대료가 오른다 — 성장과 위험을 같은 순간에 묶었다.
